01 · Fundamentos

Representar dados com JSON

Um formato de texto; seis tipos de valores. JSON não traz comportamento — define estrutura e conteúdo, legível por humanos e máquinas.

● Um sensor, quatro propriedades

objeto.json
{
  "id": "AR-007",
  "pm25": 12.4,
  "ativo": true,
  "ultimaFalha": null
}
{ }

Objeto delimitado por chavetas.

"id"

Nomes de propriedade entre aspas duplas.

12.4 · null

12.4 é um número; null é um valor explícito.

JSON é texto, não uma linguagem

Intercâmbio

Um formato

APIs, configuração e eventos podem partilhar o mesmo formato de dados.

Independência

Além do JavaScript

Deriva da notação de JS, mas é usado por muitas linguagens.

Transporte

UTF-8

Entre sistemas, usar UTF-8 e application/json.

Dimensão

Volume conta

Pode ser compacto; volume, compressão e acesso também contam.

Seis tipos de valores

tipos.json
{
  "texto": "sensor",
  "numero": 12.4,
  "booleano": true,
  "nulo": null,
  "objeto": {"id": "AR-007"},
  "array": [12.4, 13.1]
}
string · number · boolean · null

Os quatro tipos escalares.

object · array

Agregam outros valores.

raiz

Qualquer valor pode ser a raiz: 42 e true também são JSON.

Números usam ponto; códigos usam texto

numeros.json
{
  "temperatura": -3.5,
  "potenciaW": 1.2e3,
  "codigo": "007",
  "custoCentimos": 595
}
sem vírgula decimal

Nada de NaN nem Infinity.

"007"

007 não é um número JSON válido — fica string.

dinheiro

Definir unidade e política de precisão (ex.: cêntimos).

Strings, arrays e objetos aninhados

strings
{
  "local": "Viseu",
  "nota": "Sensor \"Norte\"",
  "ficheiro": "C:\\dados\\ar.json",
  "linhas": "a\nb"
}
arrays
{
  "leituras": [12.4, 13.1, 11.8],
  "grelha": [[2, 5], [21, -5]],
  "misto": ["AR-007", true, null]
}
aninhado
{
  "sensor": {
    "id": "AR-007",
    "local": {"cidade": "Viseu"},
    "leituras": [
      {"pm25": 12.4},
      {"pm25": 13.1}
    ]
  }
}
escapes

Aspas duplas delimitam; a barra invertida introduz escapes. JSON não tem tipo nativo para datas.

ordem & nomes

Arrays mantêm a ordem; sem vírgula após o último elemento. Não depender da ordem das propriedades nem repetir nomes.

Ausente, null, vazio e zero são diferentes

ausente

{}

A propriedade não foi enviada. O significado depende do contrato.

null

{"pm25": null}

Existe, mas não contém medição numérica.

vazio

{"nota": ""}

String de comprimento zero.

zero

{"pm25": 0}

É um número. Não é ausência de dados.

02 · Sintaxe

JSON válido: ler antes de confiar

Sintaxe correta deixa o parser ler o texto — mas não garante que os dados servem à aplicação. Isso é tarefa do JSON Schema.

● Desafio: encontra os quatro erros de sintaxe

inválido · para diagnóstico
{
  id: "AR-007",
  "pm25": 12,4,
  "ativo": True,
  "zonas": ["norte", "sul",]
}

Pista: verifica aspas nos nomes, vírgula vs. ponto decimal, maiúsculas em true, e vírgula final.

✎ A tua vez — edita até ficar bem formado e carrega em Verificar
Ver a correção
corrigido.json
{
  "id": "AR-007",
  "pm25": 12.4,
  "ativo": true,
  "zonas": ["norte", "sul"]
}
  1. Nome sem aspas → "id".
  2. Vírgula decimal → ponto: 12.4.
  3. True maiúsculo → true.
  4. Vírgula final removida no array.

Sintaxe correta não garante dados adequados à aplicação.

Interoperabilidade exige mais do que sintaxe

Nomes únicos

Sem duplicados

Nomes repetidos dão resultados diferentes entre parsers.

Inteiros grandes

±(2^53−1)

Em JS, Number só garante inteiros exatos até esse limite.

Datas explícitas

ISO 8601

Strings acordadas, ex.: 2026-10-01T09:30:00Z.

JSON estrito

Nada de //

Comentários e vírgulas finais são extensões, não JSON padrão.

JSON.parse lê; JSON.stringify serializa

javascript
const texto = '{"pm25":12.4}';
const dados = JSON.parse(texto);
console.log(dados.pm25);          // 12.4

const saida = JSON.stringify(dados);
console.log(saida);               // {"pm25":12.4}

if (dados.pm25 !== 12.4) {
  throw new Error("Valor inesperado");
}
parse

Produz um valor JavaScript; não valida o contrato.

stringify

Produz texto JSON para valores suportados.

eval

Nunca usar eval para ler dados.

03 · Conversão

Converter exige um mapeamento

JSON e XML não têm modelos de dados equivalentes. A conversão é uma decisão de mapeamento, não uma tradução automática.

JSON

Tipos & arrays

Tipos simples explícitos e arrays nativos. Frequente em APIs de dados.

XML

Documentos

Elementos, atributos, namespaces e conteúdo misto. Útil em documentos.

Validação

Contratos

JSON Schema e XSD descrevem contratos, com capacidades diferentes.

Desempenho

Medir

Tamanho, compressão e processamento; sem vencedor universal.

Valores XML precisam de uma decisão de tipo

xml
<sensor>
  <id>AR-007</id>
  <pm25>12.4</pm25>
  <ativo>true</ativo>
</sensor>
json
{
  "sensor": {
    "id": "AR-007",
    "pm25": 12.4,
    "ativo": true
  }
}

Convenção: preservar a raiz; escolher os tipos com base no contrato, não apenas no texto.

Elementos repetidos tornam-se arrays

xml
<rede>
  <sensor><id>AR-007</id></sensor>
  <sensor><id>AR-008</id></sensor>
</rede>
json
{
  "rede": {
    "sensores": [
      {"id": "AR-007"},
      {"id": "AR-008"}
    ]
  }
}

sensor repetido passa a sensores; manter o array mesmo com um só elemento.

Atributos e texto precisam de nomes distintos

xml
<medida unidade="ug/m3">
  12.4
</medida>
json
{
  "medida": {
    "unidade": "ug/m3",
    "valor": 12.4
  }
}

unidade e valor são escolhas deste mapeamento; JSON não define regra universal para atributos.

Uma conversão pode perder informação

Atributo ou elemento?

Uma propriedade JSON não guarda essa distinção.

Namespaces

Preservar URI e nomes qualificados quando relevam.

Conteúdo misto

Texto intercalado com elementos exige preservar a sequência.

Ida e volta

Definir regras para raiz, arrays, tipos, null e vazios; testar o retorno.

● Exercício: converte duas leituras para JSON

xml · ponto de partida
<leituras sensor="AR-007">
  <leitura><pm25>12.4</pm25></leitura>
  <leitura><pm25>13.1</pm25></leitura>
</leituras>

Na raiz JSON usa sensor e leituras; cada leitura é um objeto do array; pm25 é número.

✎ Escreve o teu JSON — o esqueleto já está preenchido
Ver a solução
solução.json
{
  "sensor": "AR-007",
  "leituras": [
    {"pm25": 12.4},
    {"pm25": 13.1}
  ]
}
  • sensor provém do atributo XML.
  • A ordem das leituras foi preservada.
  • A raiz leituras do XML não foi preservada — decisão explícita.

● Exercício: converte um contador para XML

json · ponto de partida
{
  "contador": {
    "id": "007",
    "energia": {"unidade": "kWh", "valor": 18.75}
  }
}

Usa contador como raiz; mapeia id e unidade para atributos; o número é o conteúdo textual de energia.

✎ Escreve o teu XML
Ver a solução
solução.xml
<contador id="007">
  <energia unidade="kWh">18.75</energia>
</contador>
  • 007 é um identificador textual.
  • O valor usa ponto decimal.
  • Validar o XML e testar o mapeamento inverso.
04 · Validação

Validar com JSON Schema

Sintaxe legível não basta: é preciso um contrato. O JSON Schema descreve tipos, campos, limites e padrões que os dados têm de cumprir.

Três níveis de verificação

1 · Sintaxe

O parser consegue ler o texto como JSON?

2 · Estrutura

Tipos, campos e limites cumprem o esquema?

3 · Negócio

O sensor existe? O utilizador pode enviar esta leitura?

Responsabilidades

O esquema não substitui autorização, base de dados ou regras entre registos.

$schema declara o dialeto

sensor.schema.json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.org/sensor.schema.json",
  "title": "Sensor de qualidade do ar",
  "type": "object"
}
$schema

Usar um validador compatível com Draft 2020-12. Não precisa de ser a primeira propriedade.

$id

Identifica o esquema; não implica que esteja publicado.

properties, required e additionalProperties

properties
{
  "type": "object",
  "properties": {
    "id": {"type": "string"},
    "pm25": {"type": "number"}
  }
}
required
{
  "type": "object",
  "properties": {
    "id": {"type": "string"},
    "pm25": {"type": "number"}
  },
  "required": ["id", "pm25"]
}
additionalProperties
{
  "type": "object",
  "properties": {"id": {"type": "string"}},
  "required": ["id"],
  "additionalProperties": false
}
properties

Valida cada campo quando está presente. {} é aceite; integer existe em JSON Schema, embora JSON só tenha number.

required

Array de nomes no objeto atual. Um id igual a "" ainda é aceite — para recusar, juntar minLength.

additionalProperties: false

Por omissão os campos extra são permitidos; false recusa os não declarados.

Facetas: strings, números, arrays

string
{
  "type": "string",
  "minLength": 6,
  "maxLength": 6,
  "pattern": "^AR-[0-9]{3}$"
}
format
{
  "type": "string",
  "format": "date-time"
}
number
{
  "type": "number",
  "exclusiveMinimum": 0,
  "maximum": 100,
  "multipleOf": 0.5
}
array
{
  "type": "array",
  "items": {"type": "number", "minimum": 0},
  "minItems": 1,
  "maxItems": 3,
  "uniqueItems": true
}
pattern

AR-007 é aceite; AR-7 é recusado. As âncoras ^ e $ delimitam o padrão.

format: "date-time"

Baseia-se no RFC 3339. É anotação por omissão: ativar a verificação no validador.

number

0 < valor <= 100, passos de 0.5. minimum/maximum incluem os extremos.

array

items aplica-se a todos; uniqueItems compara valores completos. [] e ["12.4"] recusados.

null vs. ausência · default documenta

number ou null
{
  "type": "object",
  "properties": {
    "pm25": {"type": ["number", "null"]}
  },
  "required": ["pm25"]
}
["number","null"]

{"pm25": null} é aceite; {} é recusado (falta a propriedade). Não existe palavra-chave nullable.

default

Documenta, não preenche. {} continua {}; o preenchimento exige lógica. title/description/examples são anotações.

● Diagnóstico: JSON válido, contrato violado

bem formado · mas inválido ao contrato
{
  "id": "AR-7",
  "pm25": "12.4",
  "zonas": ["norte", "norte"]
}

id deve cumprir ^AR-[0-9]{3}$; pm25 deve ser number; ativo é obrigatório; zonas sem duplicados. Identifica quatro falhas.

✎ Corrige os dados até passar o contrato — o mesmo validador do sandbox corre aqui
Ver a solução
corrigido.json
{
  "id": "AR-007",
  "pm25": 12.4,
  "ativo": true,
  "zonas": ["norte"]
}
  • Código corrigido para o padrão; medição passou a número.
  • ativo acrescentado após confirmar o valor.
  • Duplicado removido — confirmar que a perda de repetição é aceitável.
  • Corrigir os dados, não relaxar as regras.
05 · Composição

Compor e reutilizar regras

Alternativas, condições e coleções em Draft 2020-12. Combinar esquemas é combinar condições sobre o mesmo valor.

enum, const · $defs e $ref

enum / const
{
  "type": "object",
  "properties": {
    "estado": {"enum": ["ativo", "inativo"]},
    "unidade": {"const": "ug/m3"}
  },
  "required": ["estado", "unidade"]
}
$defs / $ref
{
  "$defs": {
    "codigo": {"type": "string", "pattern": "^AR-[0-9]{3}$"}
  },
  "type": "object",
  "properties": {
    "origem": {"$ref": "#/$defs/codigo"},
    "destino": {"$ref": "#/$defs/codigo"}
  },
  "required": ["origem", "destino"]
}
enum · const

enum aceita um dos valores; const fixa exatamente um. Maiúsculas distinguem strings.

$defs · $ref

$defs guarda esquemas reutilizáveis; $ref aplica-os onde for referenciado.

Combinar esquemas: allOf · anyOf · oneOf · not

allOf

Tem de satisfazer todos os esquemas.

anyOf

Tem de satisfazer pelo menos um.

oneOf

Tem de satisfazer exatamente um.

not

Não pode satisfazer o esquema indicado.

● Previsão: oneOf aceita o valor 4?

oneOf
{
  "oneOf": [
    {"type": "integer", "minimum": 0},
    {"type": "integer", "multipleOf": 2}
  ]
}
conta as alternativas

Para cada valor, quantas alternativas o aceitam? Testa 3, -2, 4 e -3.

Ver a solução
3 · aceite

Não negativo, mas não múltiplo de 2. Uma alternativa.

-2 · aceite

Múltiplo de 2, mas negativo. Uma alternativa.

4 · recusado

Cumpre as duas. oneOf exige exatamente uma.

-3 · recusado

Não cumpre nenhuma.

Com anyOf em vez de oneOf, o 4 seria aceite (passa nas duas).

not · if/then · fechar depois de compor

not
{
  "type": "string",
  "not": {"const": "desconhecido"}
}
if / then
{
  "type": "object",
  "properties": {
    "ativo": {"type": "boolean"},
    "instante": {"type": "string"}
  },
  "if": {
    "properties": {"ativo": {"const": true}},
    "required": ["ativo"]
  },
  "then": {"required": ["instante"]}
}
unevaluatedProperties
{
  "type": "object",
  "allOf": [
    {"properties": {"id": {"type": "string"}},
     "required": ["id"]},
    {"properties": {"ativo": {"type": "boolean"}},
     "required": ["ativo"]}
  ],
  "unevaluatedProperties": false
}
if / then / else

Se ativo for true, instante passa a obrigatório. required dentro de if evita ativar a condição quando ativo falta.

unevaluatedProperties

Considera campos avaliados pelos subesquemas (ex.: dentro de allOf). Disponível desde 2019-09; confirmar suporte.

Coleções: prefixItems · contains

prefixItems (tupla)
{
  "type": "array",
  "prefixItems": [
    {"type": "string"},
    {"type": "number"}
  ],
  "minItems": 2,
  "items": false
}
contains
{
  "type": "array",
  "items": {"type": "number"},
  "contains": {"minimum": 25},
  "minContains": 1,
  "maxContains": 2
}
prefixItems

["AR-007", 12.4] é aceite; items: false recusa posições extra. Em 2020-12, não usar array de esquemas em items.

contains

Exige entre 1 e 2 itens >= 25. [12, 30] aceite; [12, 20] recusado. O limiar é didático.

Migrar um esquema exige testes

Dialeto

Draft 7, 2019-09 e 2020-12 coexistem. Declarar o usado.

Tuplas

Em 2020-12 usar prefixItems; rever items/additionalItems antigos.

Reutilização

Preferir $defs; rever definitions nos antigos.

Ferramentas

python-jsonschema suporta 2020-12. Em Ajv, usar a classe Ajv2020.

06 · Entregar

Validar, diagnosticar e entregar

Aplicar o contrato e testar os casos que devem falhar. Uma validação só convence quando os erros aparecem onde se esperam.

Validar explicitamente com Python

python
from jsonschema import (
    Draft202012Validator, FormatChecker
)

Draft202012Validator.check_schema(schema)
validator = Draft202012Validator(
    schema, format_checker=FormatChecker()
)
validator.validate(dados)
check_schema vs. validate

check_schema valida o esquema; validate valida os dados.

formatos

Instalar jsonschema[format] e ativar o FormatChecker.

Ler um erro: localização, regra e correção

Tipo incorreto

Caminho pm25, regra type. Enviar 12.4, não "12.4".

Campo em falta

Regra required. Identificar a propriedade ausente.

Fora do contrato

Consultar minimum/maximum/pattern/enum.

Coleção inválida

Verificar items, tamanho e duplicados.

Validar na fronteira de confiança

Receção

Limitar tamanho e profundidade; tratar falhas de parsing e validação.

Segurança

Validar também no servidor. Esquema ≠ autorização.

Privacidade

Evitar dados pessoais em validadores públicos e mensagens de erro.

Referências

Controlar esquemas externos e versões; evitar resolver URLs arbitrárias.

Obrigatórios

Opcional

estado aceita apenas ativo ou inativo. Recusar campos extra.

Ficheiros

Evidência

contador.json

  "id": "EN-042",
  "energiaKwh": 18.75,
  "instante": "2026-10-01T09:30:00Z",
  "estado": "ativo"

contador.schema.json
{
